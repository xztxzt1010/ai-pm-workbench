# 产品案例：从“功能很多”到“上下文可信”

## 背景

目标用户是同时推进多个 AI 产品项目的个人产品经理。材料会持续进入：会议纪要、PRD、技术讨论、风险、测试结论、竞品研究和临时决策。传统文件夹解决了存放，却没有解决三个问题：现在应该相信哪个版本、一个结论从哪里来、缺少的信息到底是什么。

项目早期已经拥有大量功能模块，但入口分散、概念重叠，用户仍需逐页寻找项目全貌。因此本轮没有继续增加功能，而是先重做产品重心：统一知识身份、来源和关系，再建立项目上下文中心。

## 问题拆解

### 1. 信息存在不等于上下文可用

一条技术讨论可能与技术方案相关，但它不一定经过确认，也不应该自动让项目显示“技术方案已完成”。同理，发布记录不能替代测试报告。

### 2. AI 能生成不等于可以写入事实

模型适合做摘要、发现矛盾和提出候选，但正式需求、决策和风险处置需要确定性规则、人工确认与审计记录。

### 3. 本地优先不等于完全不联网

正式业务数据和凭据应留在受控边界；只有用户显式触发时，经过筛选的上下文才发送给 Provider。产品必须明确告诉用户发送了哪些来源。

## 方案

### 统一知识契约

五类工作记录共享稳定 ID、类型、状态、知识域、项目归属、来源和版本语义。关系区分 `derived_from`、`supports`、`contradicts`、`relates_to`、`supersedes`，AI 建议的关系在确认前不是正式关系。

### 项目上下文中心

八类上下文固定为：项目目标、用户需求、PRD、技术方案、开发状态、测试状态、风险列表、决策历史。每类只由定义好的正式对象判定“已有”，候选材料单独展示，缺口不会被模型补写。

### 有边界的 Agent

Agent 收口为产品分析、技术分析、项目管理、知识整理四类。每个 Agent 固定输入范围、允许工具、输出 Schema、成本档位和 Eval；输出进入草稿/提案区，不直接改变正式状态。

## 典型流程

```text
会议原文
  ↓ 稳定分段与证据定位
需求候选（AI / 人工）
  ↓ 编辑、提交、人工确认
正式需求版本
  ↓ 项目上下文聚合
状态与缺口 + 可打开来源 + Markdown 快照
```

## 失败策略

- Provider 离线：保留完整人工记录、检索、确认与导出能力。
- 模型输出不符合 Schema：整次拒绝，不写半条正式数据。
- 跨项目来源：领域层直接拒绝，而不是静默混入或过滤。
- Sidecar 中断：最多一次受控恢复，不自动重试可能计费的旧请求。
- 恢复数据库：先做完整性检查和恢复前快照，再由用户确认。

## 验证方式

工程门禁包含领域规则、Service、Repository、UI、Sidecar、migration、安全、Agent Eval、性能和包体预算。人工门禁则单独覆盖真实项目、来源下钻、Windows 安装、凭据、升级/卸载、通知、缩放和键盘路径。

这种分离很重要：测试绿灯可以证明契约没有明显回归，但不能替代真实安装环境与真实用户任务。

## 结果与反思

这次迭代最有价值的结果不是新增一个 AI 按钮，而是建立“候选与事实分离”的产品语义。用户能在一个页面看见项目材料是否可信、是否过期、缺什么、来自哪里。

下一步也不是扩大功能面，而是用真实项目与干净 Windows 环境补齐证据。只有这些门禁通过，完整源码和安装包才适合公开发布。
